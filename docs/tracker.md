# Tracker

backlog 的正本，由实现方在改动所属的 PR 里记账，`limae-orchestra` 负责合入后核对与串行编排动 tracker 的 PR。这是本仓对全局守则「多 agent 协作」那条 (tracker 只由 orchestra 在合入后记账) 的有意偏离，理由是记账与改动原子落地、不挂在「记得」上，且读数在实现方手里是第一手的；冲突由编排上的串行解决，不靠限定作者。规则语义的正本在 `spec/rules.md`，这里只记还没做的事与一句话去向；证据链在 `docs/research/`。

- **`--all` 的未跟踪文件 note** (2026-09-08)：**已被上一条取代，以下是当时的读数，不是今天的行为** —— note 与它所补的 Git 索引选择都已在 [PR #170](https://github.com/Luolc/limae/pull/170) 删除。`--all` 走的是 `git ls-files '*.md'`，语义是「所有**被 git 跟踪**的 Markdown」 —— 已跟踪文件的改动照查，漏的只有还没 `git add` 的新文件。这个语义不改 (pre-commit 的 `--all-files` 是同一个形状，是 git-based 工具的通例)，改的是它的**失败方向**：新写一个 `.md`、`git add` 之前跑 `limae --all`，此前报 `OK: N file(s) clean` 并退出 0，而报绿会关掉下游复核 —— 一个在「真的干净」与「有新文件根本没被看见」两种情况下给出相同输出的观察，不能用来在两者之间做选择。现在这种情况向 stderr 打一行 `note: N untracked *.md not checked (git add them to include)`。

  五条边界：写 stderr 不写 stdout (stdout 是供人 parse 的结果，这是诊断)；退出码一律不变，它是 warning 不是 error，改退出码对所有消费方都是破坏性变更；被 `.gitignore` (git 侧 `--exclude-standard`) 或 `.limae-ignore` (`not_ignored`) 忽略的不计数 —— **总在喊的告警等于没有告警**；只在 `--all` 路径打，显式传文件 (pre-commit 那条路) 没有这个盲区；不加开关 (YAGNI)。

- **一键安装：`install.sh` 与 Homebrew tap** (2026-09-11，PR #171)：用户要「majority 的普通用户一键装完只需 source 一下或开新 terminal，保留 env var 的口子给要 customize 的人」。两条路装的是同一批 Release 二进制。**`install.sh`** (仓根) 的契约：`main "$@"` 在最后一行才调用，管道截断时不完整的脚本不会跑到一半 (rustup / ollama 有这层，deno / bun / dprint / starship 没有)；sha256 三个后备 `sha256sum` → `shasum` → `openssl`，**一个都没有就失败而不是跳过** (uv 在没有 `sha256sum` 时静默跳过，是反面样本)；认不出的 OS / CPU **报错并列出四个 target**，不静默回落 x86_64 (deno / bun / dprint 会)；Linux 一律 `*-unknown-linux-musl`，不探测 libc，因为 Release 只有静态 musl 一份；装进 `~/.local/bin`，不用 sudo。三个旋钮：`LIMAE_VERSION` (Release tag，默认取 `/releases/latest` 的重定向)、`LIMAE_INSTALL_DIR` (默认 `~/.local/bin`)、`LIMAE_NO_MODIFY_PATH` (非空则一个文件都不写，只打印要加的那行)；**给了位置参数是报错，不是忽略**。PATH 默认改 rc，这是 orchestra 对七个安装器横向调研 (rustup / uv / deno / bun / dprint / starship / ollama，2026-09-10，产出留在 `~/scratch/`、未进仓) 的裁决，与那份调研自己的建议相反 —— 那条建议是照着维护者一个人的 dotfiles 优化的，而用户要的是 majority：已在 PATH 就什么都不写，否则按 `$SHELL` 写一个成对标记的块；rc 被 chezmoi 管 (`chezmoi source-path` 认得) 则只打印不写 —— 写进去会在下次 `chezmoi apply` 时消失，用户看到的是「装过了又没了」；fish 与其它拿不准 rc 语法的 shell 同样只打印 (给 `fish_add_path`)。**只给 zsh 与 bash 写文件**，macOS 上的 bash 按 bash 自己的登录查找顺序挑第一个存在的 (`.bash_profile` → `.bash_login` → `.profile`)，直接建 `.bash_profile` 会遮掉正在用的 `.profile`。**不写 `~/.local/bin/env`** —— 要写的只有一行 `export PATH=…`，它是关于那个目录的、不是关于 limae 的，而 uv 也往那个文件写。脚本由 `ci.yml` 的 `build` job 复制进 `site/`，所以 `https://limae.luolc.com/install.sh` **由构造保证等于仓里那份**，不靠谁记得同步 (deno 的 `SHA256SUM` 只覆盖仓内副本、与 `deno.land` 实际送的字节已经漂开)。**Homebrew** 的 formula 由 `tools/render_homebrew_formula.sh` 渲染、`release.yml` 新增的 `homebrew` job 推 `Luolc/homebrew-tap`，secret `HOMEBREW_TAP_TOKEN`；`release.yml` **只在末尾新增，既有 job 一个没重排** (job 顺序前后逐行比过)。
  **`homebrew` job 做成两个触发器都跑，只有推 tap 那一步 `if: push`** —— 这是本条最值得记的形状。brief 原本的安排是「`brew install` 这一臂本机跑不了，留给用户在 Mac 上补一次」。改成 CI 门之后，`workflow_dispatch` 对着一个已有 tag 就能把 `brew audit --strict` / `brew install` / `brew test` 整条跑完，而**人手工补的那一次只证明「那天在那台机器上可以」，CI 里的这条每次都证明**。formula 的 `test do` 也是两臂：一份合规文件必须过，一份违规文件必须非零退出并报出 `zh-typography-4` —— 只跑 `--help` 的 test 对「装上了且真能 lint」与「装上了但什么都不查」给出相同输出。
  **三处已知缺口，明写**：① **`brew audit` / `brew install` / `brew test` 一条都没跑过** —— 开发机是 Linux 且没有 Homebrew，**连 `ruby -c` 都做不了，机器上没有 ruby**，所以「formula 渲染出来了」这个观察对「formula 能装」与「语法对但装不起来」给出相同输出，没拿它当验收；`brew tap-new --no-git` 等用法只对着 Homebrew Manpage 核过文档、没有运行过。**第一次 `workflow_dispatch` 就是这三条命令的第一次运行，可能红**，建议在推任何 tag 之前先跑一次。② macOS 与 aarch64 上的 `install.sh` 没跑过 (本机只有 x86_64 Linux)。③ `LIMAE_INSTALL_DIR=/` 在 root 下真正装成功那一臂没跑 —— 那要把 limae 装进共享开发机的 `/`。
  **验收读数** (2026-09-10/11 dev-oregon，全部裸跑、单独看退出码)：正臂是干净 HOME (`/etc/skel/.profile` seed) 装完后在新终端里**真检查一个文件**、命中 `zh-typography-4` 退出 1，同一个 shell 里一份合规文件退出 0 —— 少了后半条，「真在查」与「见谁都报」分不开。对照臂：改一个字节 → 报 checksum mismatch、什么都不装，**同一条路上字节不动的正臂装成功** (一道把什么都拒掉的门在负臂上同样绿)；假 `uname` 报 `riscv64` / `SunOS` → 失败并列出支持项；连装两次 → rc 里只有一个块；PATH 上抽掉三个 sha256 工具 → 失败退出，加回 `sha256sum` → 装成功；chezmoi 在 PATH 上 → 不写 rc，同一个 HOME 把 chezmoi 从 PATH 拿掉 → 块写进去了。改字节那两臂要控制服务的字节，跑在本地 HTTP 服务上、用的脚本副本**只改了传输那两行**，校验逻辑一个字节没动。
  **三轮审查，第 2 轮是修第 1 轮时引入的回归**：① `install.sh` 的幂等只匹配开标记 `# >>> limae >>>`，rc 里留着一个未闭合的块 (中断写入、手工编辑、合并冲突) 就被读成「块已存在」，PATH 行永远不写，而输出说一切正常 —— 改成两枚标记都在才算。② 修①时为另一件事加的 `${bin_dir%/}` 把根目录 `/` 削成空字符串，`LIMAE_INSTALL_DIR=/` (改之前能走的值) 下载完才在 `mkdir -p ""` 上失败；改成 `case` 里放过 `/`。**这个形状与 #170 上「修第二个引入第三个」是同一个**：修一处时顺手加的归一化，本身也是一次行为改动，要按行为改动验收 —— 逐值两臂 (`/` `//` `/opt/limae/` `/opt/limae` `$HOME/.local/bin/`) 里只有 `/` 那一行从 `[]` 变 `[/]`、其余四行两臂相同，那一列才是「没顺手改坏上一轮那个修复」的对照臂。**判错的地方也记下来**：动手时想到过 `/`、判定它是病态输入就放过去了，错在把「不为明显不合理的输入写负向断言」用在了「别把合法值改坏」上 —— 前者是不加新防线，后者是不许改坏已有行为，两件事。

## 分发调研产出 (`docs/research/distribution-python-ecosystem.md`、`docs/research/distribution-cross-ecosystem.md`)

- **两份调研已入库，其中的建议一件都还没实施。** 第一份 (2026-09-09) 聚焦 Python 生态，头号参照 ruff；第二份 (2026-09-09) 把范围扩到 Node / TypeScript，头号参照 AutoCorrect，并在其第 8 节明写了对第一份部分推荐的修订，第一份开头已加按语指回第二份。
- **第二轮 (以此为准) 的核心结论**：GitHub Release 的预编译二进制是唯一真相，外面只套两层薄启动器 —— PyPI 侧用 maturin `bindings = "bin"` 打平台 wheel (`py3-none-<platform>`)，npm 侧用 biome / dprint 式的 `optionalDependencies` 平台包；两者都从同一份 Release 产物打包，不重新编译。**不做**：任何语言的 FFI 绑定 (napi-rs / pyo3 扩展模块 / rb-sys / JNI)、官方 GitHub Action、LSP。判断依据是 AutoCorrect 这个对照臂：五家 FFI 绑定里三家已落后 Release 两个小版本以上，多语言绑定换来的是版本分叉、不是覆盖面 (第二份 §1、§4)。
- **配置文件 canonical 维持 `limae.toml`**：`[tool.limae]` 只作 Python 项目的适配器，不当主入口；第二轮因前端仓没有 `pyproject.toml` 而把这条判断加硬 (第二份 §8)。
- pre-commit 侧沿用第一轮的 tiny mirror 仓 (`limae-pre-commit`, `language: python` 依赖 PyPI wheel) 方案，未改。
