# ADR-0016：hook 只做机械排版修复，按批就地修，跨批靠前缀重放

- 日期：2026-09-11
- 取代：ADR-0009 §二–§五、§八 (按批缓存末批整段改写、A/B 对照、编号、`Stop` 回注、引擎隐私边界)；ADR-0011 全部 (A/B 回注只带编号)；ADR-0012 全部 (单路润色的会话态记录)；ADR-0014 全部 (Codex 的 `Stop` hook)；ADR-0008 §十 P0 (hook 里的一次输出润色与 A/B 采集)。处置细节见 §八。
- 承接：ADR-0009 §一 (挂 `MessageDisplay`，改写只上屏)、§六 (失败 fail-open)、§七 (先在本仓自试，再交 machine-setup) —— 这三节的内容由本 ADR 承接并成为唯一依据；ADR-0005 §四 (确定性段与语义段的两段式边界)；ADR-0008 §二 (三个子命令) 与 §六 (hook 失败就用原文)。

## 背景

ADR-0009 将 hook 设计为「按批缓存、末批整段送模型改写、按概率双跑 A/B 盲评」，ADR-0012 又要求每次单路润色留下会话态记录，ADR-0014 再把同一套机制搬到 Codex 的 `Stop` 上。这套设计在本仓试了十天 (2026-09-01 起)，用户于 2026-09-11 决定收缩。六条决定是本 ADR 的输入，不在本 ADR 的讨论范围内：

1. **polish 这个 feature 保留**：`rust/polish/` 一行不删，`limae polish` 子命令一行不动。只改「hook 不再调 polish」。
2. **hook 只保留纯机械的排版修复**，即 `limae --fix` 那一套，不再调用模型改写。
3. **彻底移除「润色版 vs 原版」的对比**：A/B 盲评及其证据用途一并停止。
4. **放弃 Codex 一侧的 hook**。理由来自实测 (ADR-0014「实测」一节)：Codex 没有与 `MessageDisplay` 等价的替换事件，hook 输出只能作为 `systemMessage` 追加在回复**下方**，既不渲染 Markdown，也无法替换原文 —— 「修排版」的功能放在那里没有意义。
5. **polish 有两条并列的消费路径、一个源文件**：它仍是 CLI 功能，想跑的人照样可以跑，也可以作为 headless tool 使用；同时另行提供一份**生成出来的 skill**，供人直接装进自己的 agent，让模型在**写的时候**就遵守规则 —— 对 coding agent 来说，skill 是更 native 的用法。两条路径共用 `spec/polish/` 这一份源文件。skill 的生成往后排 (用户要先把 polish 的 prompt 再测一测)，本 ADR 只保留指针 (§七)。
6. **配置沿用现状，用户级配置本期不做**：hook 读取的规则配置仍是今天 `find_config` 从 `cwd` 开始找到的仓级配置，没有就用默认集。用户先前提出的用户级 `~/.config/limae/limae.toml` (仓级覆盖用户级、一个「不读仓级」的开关、存在就读且永不创建) 已由用户自己收回 —— 包括他自己在内，大多数用户都使用默认配置，因此暂不实现；讨论中明确的判据留在 §三 的开放项里，不是本期契约。

前四条由 orchestra 在 brief 中转达；第五、六条是用户在 orchestra 会话中口头补充的 (语音输入，第六条前后说了两次，以收回那次为准)，经 orchestra 转述，本 ADR 未亲闻，措辞表达的是原意而非逐字记录。用户同时指出：这次改造**最重要的是跨批时如何判断是否在围栏内** (§二)，其他都只是删代码。

改造由四条实测读数支撑，均由 `limae-orchestra` 于 2026-09-10/11 在本机 (dev-oregon) 亲手测得，本 ADR 引用时保留测法。**读数 B 是本设计的关键依据**，其余三条决定边界与预算。

**读数 A —— `MessageDisplay` 的批次边界始终落在行边界上。** 测法：在 `.claude/settings.local.json` 中为 hook 命令包一层 `tee`，将宿主送来的原始 payload 落盘后再喂给 `limae hook`，行为不变。一个 session 采到 58 条真实 payload (6 条消息)：`final=false` 的中间批次 52 条，**52 条均以 `\n` 结尾，0 条反例**；`final=true` 的末批 6 条，**0 条以 `\n` 结尾** —— 这是本观察的对照臂，证明「以 `\n` 结尾」这一判据能区分两种情况，并非恒真。围栏代码块内部也按行发送：一个 ``` 块会拆成「开栏行 / 每行内容 / 收栏行」若干批。

**读数 A′ / B′ (orchestra 2026-09-11 补测，经 herdr 转达)**：将 hook 换成对每个非末批返回 `〖MARK<index>〗 + delta` 的预实验，5 个非末批的标记都按位置出现在屏幕上，末批按设计没有 —— **中间批次的 `displayContent` 会被宿主采纳**，这是 §一「按批就地替换」的第一手证据 (第一次预实验只打 `index==1`，又指错位置，一度误判为「宿主丢弃中间批次」，问题在于位置判断，不在宿主行为)。同一次实测中，index 1 的 delta 是 `"甲。\n\n乙。\n\n"`：**一批可以有若干整行，不是一行**，任何按「一批一行」实现的逻辑都是错的，边界仍在行上。payload 的字段：`delta`、`final`、`index`、`message_id`、`cwd`、`session_id`、`transcript_path`、`scratchpad_dir`、`prompt_id`、`turn_id`、`hook_event_name`。

**读数 B —— 逐行修等于整篇修，当且仅当带着「我在不在围栏里」的状态。** 测法：取 session transcript 中 orchestra 自己的回复原文 250 篇 (transcript 保存的是未经 hook 改动的原文)，每篇各跑两次 `--fix`：一次整篇，一次逐行送入后拼回，归一化尾换行后逐字节比较。**248 篇完全一致，2 篇不一致；2 篇的差别都在围栏代码块内**，且形状相同 —— 整篇修得到 `result.status.success()`、`..limits() }`，逐行修得到 `result.status.success ()`、`..limits () }`：逐行送入时，规则不知道该行在围栏内，于是把「英文与括号之间加空格」套到 Rust 代码上。不带这个状态的失败形态最糟：0.8% 的概率、静默、改坏代码。另记一个测量陷阱：该实验第一版读数是「250 篇 0 篇一致」，这是假的，差别全在测量循环自行补上的一个尾换行字节 —— **100% 的读数本身就是可疑信号**，必须展开看。**「当且仅当」是这 250 篇的读数，不是规则集的定理**：规则集还有几处跨行状态 (行内指令的成对形态、跨行的行内代码 span)，样本中一次都未出现，§二因此不按样本挑状态，而是重放全部前文。

**读数 C —— 机械修的成本比 polish 低三个数量级。** `target/release/limae --fix` 处理 3.4 KB 中文正文，20 次减去纯 `cp` 对照臂后**约 12 ms 一次** (含进程启动)；debug 构建约 59 ms。对照：`rust/polish/engines.rs` 的 `RUN_TIMEOUT` 为 600 s，`rust/hook/block.rs` 的 `TIMEOUT` 默认 60 s，`.claude/settings.local.json` 为 `MessageDisplay` 配置的 `timeout` 是 120 s。

**读数 D —— 机械修不可省略：一半回复都需要它。** 同一批回复原文 791 条，677 条够长 (≥ 60 字符)，运行 `--fix` 后 **353 条被改动、324 条本来就干净，改动率 52.1%**。抽样查看改动内容，全部是排版：`**十二道门**(含…` → `**十二道门** (含…`、`判据文化——没有` → `判据文化 —— 没有`，没有一条改动语义。

有一条旧读数不能作为本 ADR 的证据，写在这里避免误用：同一 session 的 `diagnostics.jsonl` 中有 `fix/repaired` 103 次。`rust/hook/block.rs` 的 `shown()` 接收的是引擎重写结果，**这 103 次记录的是机械修改动了 polish 输出，不是改动了模型原文**；读数 D 才是「原文需要机械修」的读数。

本 ADR 只作决定，**不改一行 Rust**；代码改造属于下一个任务，它以本 ADR 为规范，验收判据见「验收判据」一节。

## 决定

### 一、hook 的新合同：每批就地修，输出替换该批

hook 仍只挂 Claude Code 的 `MessageDisplay` (ADR-0009 §一 的依据不变：它是 display-only，「the stored message and what the model sees are untouched」，被修文本永远不写回 transcript，也不进入模型上下文)。变化在于每批的处理方式：

- **输入**：一条 `MessageDisplay` 事件。仅使用 `hook_event_name`、`session_id`、`message_id`、`turn_id` (与 `message_id` 一起构成 §二 的消息实例键)、`index`、`final`、`delta`、`cwd`；其余字段即使读到也不用。
- **处理**：将这批 `delta` 视为一段 Markdown，运行与 `limae --fix` 完全相同的确定性修复 (同一条 pipeline、同一个不动点语义)，但送入 fixer 的不是这批文本本身，而是这条消息截至当前批的全部原文；输出取修后文本中属于这批的行 (§二)。不再设短消息阈值：机械修对任何长度都正确且便宜，`LIMAE_HOOK_MIN_CHARS` 随之退役。
- **输出**：修后文本与 `delta` 不同时，输出 `{"hookSpecificOutput": {"hookEventName": "MessageDisplay", "displayContent": <修后文本>}}`；相同时**不输出任何内容**。修后文本的结尾必须与 `delta` 逐字节一致 —— 有 `\n` 就保留，没有就不加，因为 `displayContent` 替换的是整批文本，少一个换行就会把两批粘成一行。
- **中间批与末批一视同仁**：末批不再有特殊地位，只是最后一个需要修的批次；`delta` 为空 (消息以换行结尾时末批为空) 则不输出。
- **失败 fail-open**：任何一步失败，这批不输出，原文照常显示，退出码 0，并在会话态 `diagnostics.jsonl` 中记一行 (§五)。这一条从 ADR-0009 §六原样承接，宿主对 `MessageDisplay` 失败也这样处理。
- **`Stop` 事件不再处理**：收到后不输出。它此前仅为 A/B 回注而挂，A/B 停止后就没有用途。Codex 的 `Stop` 也不输出 —— `.codex/config.toml` 由下一个任务删除，但即使残留配置仍指向 `limae hook`，进程也只会静默退出 0。
- **`LIMAE_HOOK_DISABLE` 保留**：非空时整个进程立即退出 0，作为会话级总开关。它此前还承担递归防护职责 (hook 调起的引擎本身也是 agent)，现在 hook 不再启动任何子进程，这部分用途消失，开关本身保留。
- **预算**：hook 不再有任何超时旋钮，`LIMAE_HOOK_TIMEOUT`、`LIMAE_HOOK_AB_RATE` 随引擎和 A/B 一起退役。一批成本是整篇重修的十几毫秒 (读数 C；orchestra 同日补测，最长一条消息 12.9 KB，整篇修一次 13 ms，release 构建) 加 §二的兄弟批等待 (上限 2 s)，落在宿主给 `MessageDisplay` 的默认 10 s 内，因此 `.claude/settings.local.json` 不再需要 `timeout`。

这条合同与 ADR-0005 §四的两段式边界一致：hook 只做确定性段，语义段 (polish) 留在 `limae polish` 与将来的 skill 中 (§七)。

### 二、跨批靠前缀重放：存原文，整篇重修，只取这一批的行

读数 B 表明：将一条消息拆成批次来修时，与整篇修的分歧来自「过去决定现在」的状态 —— 样本中出现的是围栏代码块 (`spec/rules.md`「全局豁免」第 1 条)，规范中同类的还有跨行行内指令、段落分组、跨行行内代码 span。本 ADR 第一版只保留一个「是否在围栏内」的布尔；审查方 (PR #178 两轮) 与 orchestra 分别独立指出其问题：hook 自己数围栏行，就会出现第二个「什么算代码」的来源，块模型一变 (缩进代码块、围栏长度匹配) 布尔就不够，也没有检查会提醒；跨行指令与 span 更无法用一个布尔表达。**裁定改用 orchestra 提出的前缀重放**：hook 中不写任何解析器，所有「过去决定现在」的状态 (围栏、成对指令、`disable-next-line`、段落分组) 都由 canonical pipeline 计算，并始终与 `limae --fix` 同源。

**「单一真相来源」是耦合性质，不是正确性保证，必须分开说。** orchestra 最初的论据「crate 已有一套处理 `~~~`、围栏长度、缩进代码块的块解析器，复用它就能免费得到这些能力」**是错的**，经独立裁决方证伪，orchestra 复读源码确认 (2026-09-11)：`rust/markdown.rs` 与 `rust/hook/render.rs` 中的围栏判断都只是同一个布尔翻转 (`starts_with("```") || starts_with("~~~")`)，既不处理「闭合围栏不得短于开启」，也不处理 4 空格缩进代码块 —— 这些结构当前在 CLI 与 hook 两侧都会被当作散文修。前缀重放得到的是「hook 永远不会与 linter 分叉，linter 日后变强时 hook 自动跟上」，仅此而已；它承诺的是**等于当前 `limae --fix`**，不是「不破坏 CommonMark 所认为的代码」。后者属于共享解析层、规范和黄金集，不能借 hook 方案宣称已经解决。

真正的裁决依据是实测。orchestra 于 2026-09-11 组织两个独立裁决方 (gpt-6-astra high、Claude Fable 5.1 high，footer 实读；两份报告由 orchestra 另开 PR 原样入库至 `docs/research/`：[`hook-batch-fence-debate-astra.md`](../research/hook-batch-fence-debate-astra.md)、[`hook-batch-fence-debate-fable.md`](../research/hook-batch-fence-debate-fable.md) —— 注意 Astra 的结论对应 head `b20bc03`，不是最终版)，分别从不同路径得出相同结论 —— 两份原案都不能保证「逐批等于整篇」，建议采用带保守放行的前缀重放。Fable 用 52 条黄金 fixture 逐行切批实测：围栏计数方案有 7 条与整篇分叉 (指令跨批 3、跨行反引号 span 4)，前缀重放有 3 条，**且这 3 条是任何按批方案都无法消除的** (前一行已上屏，后一行才改变其保护状态)；Astra 在 37 条可分批 fixture 上得到同样的 6 比 3，并给出条件性的不可能性结论：在「只能替换当前批、不能回改前批」的宿主合同下，任何算法都不能在全输入上逐字节等于整篇，要么接受歧义区段少修，要么改变显示协议。本 ADR 采用前者，也就是下面第 3 步的两道 fail-open。

**每批都是新进程，状态只能经磁盘传递。** 状态就是**这条消息截至当前的原文**，按批分文件：第 `k` 批将自己的 `delta` 原文写入 `parts/<消息实例键>/<k>.part`，实例键由 `message_id` 加 `turn_id` 构成 (为什么不只用 `message_id`，见下文「消息实例身份」) (沿用 `rust/hook/state.rs` 的 `keep`：位于 `$TMPDIR/limae-hook/<session_id>/` 下、位置没有配置项、不允许落在任何 checkout 内、目录 `0700`、文件 `0600`、先写临时名再 rename)，然后：

1. **等待第 `0` 到 `k-1` 批的文件齐全** (第 `0` 批无需等待)。宿主并发派发各批，不等前一批结束 (2026-09-01 在 Claude Code 2.1.257 上实测)，因此需要等待，上限沿用 `SIBLING_WAIT` 2 s、`SIBLING_POLL` 20 ms；到期仍缺任何一批时，这批原文放行，记录 `siblings` / `incomplete`。按 index 分文件、读取时拼接，而不是追加到一个文件中 —— 并发写同一文件会产生顺序要求，分文件天然没有竞态。
2. **拼出前缀 `P` = 第 `0` 到 `k-1` 批的原文**，`T = P + delta`。
3. **两道当批 fail-open 都表示「现在还无法判断」**，命中任一条就让这批原文通过、记录一行诊断、停止后续处理：
   - **行边界不完整** (`siblings` / `partial`)：`P` 非空且不以 `\n` 结尾，或这批不是末批而 `delta` 不以 `\n` 结尾。前者表示上一批从一行中间截断，这批从行中间开始，按行截取的输出会把前半行再显示一次；后者表示读数 A 的前提被宿主打破 (52/52 中间批以 `\n` 结尾、6/6 末批不以 `\n` 结尾，那个对照臂证明判据能区分)。状态保存的是原文，因此**不需要向后传播**：下一批的 `P` 仍是合法原文，它自行按这两条判断。
   - **尾部可能仍在一个行内代码 span 中** (`siblings` / `unclosed`)：`T` 末尾有一段反引号串，按 `spec/rules.md`「全局豁免」第 2 条，它仍可能被**未来的行**以等长串闭合 (span 可跨行，只受空行与块起始截断)。这是唯一一种「未来决定过去」的语法：开反引号的那批若按散文修了，下一批闭合 span 时即使重放，也只能替换下一批，无法撤回已经显示的改动 (审查方于 2026-09-11 使用 `spec/fixtures/span-across-line-break` 实测：整篇仅报告 span 外的 `后文(y)`，逐批时第一批另报告 span 内的 `zh-typography-1`)。**这一信号由 canonical Markdown 扫描器 (`rust/markdown.rs`) 提供，hook 不另写反引号解析器** —— 否则又会产生第二个真相来源。围栏没有这个问题：开栏行当场决定后续行是代码，属于「过去决定现在」，重放本就能处理。

     这条决定有实测依据，不只是架构偏好。orchestra 于 2026-09-11 在本机做三臂实测 (release 构建)：未闭合反引号的 `` `foo(),bar() `` 被修成 `` `foo (),bar () `` (被当作散文修改)；已闭合的 `` `foo(),bar()` `` 未改动 (对照臂：span 确实受到保护)；完全没有反引号的 `foo(),bar()` 被修成 `foo (),bar ()` (对照臂：判据有分辨力)。此前围栏的三臂读数则是**未闭合围栏受保护**。因此，「未闭合就当代码」**不是普遍规律** —— 围栏与行内 span 在这一点上不对称，任何依据这种直觉实现的方案都会在其中一侧出错，只有让判断来自同一个扫描器才能避免分叉。**两道 fail-open 也不是并列的两个保险**：围栏那批即使判断错，尚未上屏，重放仍能补救；span 那批已经画到屏幕上，之后如何重放都无法撤回 —— 后一道防的是不可逆的情况。
4. **`T' = fix(T)`**，使用与 `limae --fix` 相同的 pipeline、同一份配置 (§三)。
5. **运行时断言 `lines(T') == lines(T)`**：R 家族「不增删行」是 `spec/rules.md`「处理单位」规定的契约，黄金 fixture 据此断言，orchestra 又在 677 篇上实测 677/677 不变 (对照臂故意加一行，判据报 22→24)。断言失败即为 bug，这批原文放行，记录 `fix` / `crashed`。
6. **按原始 LF 字节截取本批**：在 `T'` 中跳过 `P` 含有的 LF 数，剩余全部字节原样作为这批的 `displayContent`，包括 CR 与尾 LF，结尾与 `delta` 逐字节一致；空 `delta` 直接不输出；与 `delta` 相同也不输出。不使用「最后 `lines(delta)` 行」的表述 —— `"甲\n乙\n".split('\n')` 会带一个虚拟尾空串，两种计数法会相差一行 (Astra 报告指出的测量陷阱)。验收必须走 `Pipeline::fix`，不能用 CLI 文件 I/O 输出冒充 hook 的字节合同：CLI 那一层会将 CRLF 归一化为 LF。

**失败一律倒向「不修」**：误以为在围栏 / span 外而实际在内，会静默且罕见地改坏代码；反过来只会漏修一处排版。因此，上述每条 fail-open 都是原样输出这批。

**代价必须明确写出，不藏在实现中：回复原文会留在磁盘上。** 第一版 §二只保存整数，磁盘上没有原文；改成前缀重放后，每条流式消息的原文按 `message_id` 保存回会话态目录，这是为「没有第二个真相来源」付出的代价。这并不比今天退步 —— 当前 `state::keep` 保存的就是 `delta` 原文，ADR-0009 §八与 ADR-0012 的整套边界也正是为它而设 —— 但这套边界必须**完整继承**：位于 `$TMPDIR` 下、`state::root` 拒绝落在 checkout 内、`identifier` 折叠 id 中的非常规字符、`0700` / `0600`、不入库、不经 agent 间通道传递。

**清理**：消息分片目录**不再由末批删除**，改由既有的 `prune` 按 `ORPHAN_RETENTION` (1 小时) 清除 —— 末批可能与其之前的某批同时运行，末批删目录会让那一批读到「目录不存在」，白等到期。会话目录仍按 `RETENTION` (24 小时) 清理。**消息实例身份**：若宿主复用 `message_id` (中断后重发)，旧一代分片会成为新一代的前缀。Astra 用合成实验证明这并非纯理论风险：当前代 index 0 已覆盖、index 1 尚未到达，而目录中留下旧代 index 1、index 2 已到达 —— 编号连续性检查通过，缺失的那批本应是开栏行，旧文件却是普通文本，新消息中的代码被改为 `foo ()`。**编号齐全只能证明文件存在，不能证明它们属于同一次消息。** 同一报告也指出，`state::identifier` 是路径清洗而非标识符 (折叠非常规字符、截到 64 字符，不同输入可能落到同一路径；由源码确认，不代表宿主曾发生碰撞)。处置采用最小机制：分片目录的键由 `message_id` 改为 `message_id` 加 `turn_id` (payload 已有该字段)；同 index 重送相同内容时幂等，**内容不同则该实例作废** —— 写入作废标记，本批和后续各批均原样放行，记录 `siblings` / `incomplete`，不得悄悄覆盖。两条前提由实现任务验证，不作为保证，**验不成时的处置也在此确定，不允许静默退回**：① `turn_id` 在各批间一致且随重发变化 —— 若验不成 (字段缺席、不一致、或不随重发变化)，实现任务停止，回到本 ADR 与用户裁决，**不得静默退回只按 `message_id` 分目录**；若只是「不随重发变化」，机制等于未增加，失败方向仍是旧前缀污染 —— 那是协议缺少信息，不能说「index 0 清空就能解决」。② 宿主 id 是 UUID 格式 (若是，`identifier` 的折叠对其为恒等映射) —— 若验不成，实例键改用完整身份的安全编码或摘要 (例如对 `session_id` / `message_id` / `turn_id` 原串取哈希后作为路径段)，**不得继续把 `identifier` 的折叠和截断作为唯一键**。

**成本是「总量大、单批有界」**：每批都重修一次前缀，总量为 `sum(|P_k|)`，不是一次 13 ms。两个裁决方的读数 (2026-09-11 本机 release)：Astra 将 12.9 KB 切为 120 批，串行工作量合计 4.47 s (不等于用户等待 4.47 s，宿主是否重叠执行未测)；Fable 测得 200 KB 单次 151 ms，100 KB 切为 598 批合计 28 s，**但每批有界**。宿主对单批的预算是 10 s，因此单批不是问题，极长消息的累计工作量才是问题。实现必须为**原始字节数、分片数、单次等待**分别设置上限，超过后停止修该实例 (后续各批原样放行，记录 `siblings` / `incomplete`)，**不能截掉旧前缀后继续修** —— 那会再次丢失围栏和指令状态。上限数值由实现任务确定。

**不再需要的**：`transcript_path` (不读取 transcript，流式期间它是否包含当前消息未核实，而且它是回复原文，本 ADR 有意不碰)；`parts::assemble` 的整篇拼接逻辑**保留** —— 它拼的正是前缀 `P`，只是不用再等到末批才调用。

### 三、配置沿用现状；用户级配置是开放项，本期不实现

hook 读取的规则配置**一个字不改**：从事件的 `cwd` 开始，按当前 `find_config` 发现 —— 逐层向上，每层先查 `limae.toml`，再查 `pyproject.toml` 的 `[tool.limae]`，**遇到含 `.git` 的层就停止**，不离开仓库继续向上；一层也没有找到时使用默认集。它与 `limae [--fix] FILE...` 读取的是同一份配置，README 中「规则选择写进配置文件，仓库自己跑的 limae 与这条 hook 读到的才是同一份」仍然成立。

**配置错误的处理与 CLI 相反**：CLI 报错并退出 2，hook fail-open —— 这批原文放行，记录一行 `fix` / `config` (§五)。这不是新决定，而是 ADR-0008 §六「失败语义分场景」在配置项上的落实。

**开放项 (不在本次决定范围内，实现任务不得顺手当待办做)**：用户曾提出用户级配置 `~/.config/limae/limae.toml`，随后自己收回 —— 大多数用户 (包括他) 都用默认配置。若将来确有需求，以下几条是当时已经明确、不应丢掉的判据，届时另起 ADR，从这里继续：

- **只读、永不创建**：`install.sh` 不 `mkdir -p`，首次运行不写模板，缺文件不报 warning、不记诊断 —— 缺席是正常状态，不是需要修复的状态。
- **「不存在」与「存在但读不了」必须有不同的行为**：前者静默使用默认并照常修；后者这批不修，记录 `config`。否则用户写错一个键，行为会悄悄回退默认，而他以为配置已生效 —— 分辨力来自「屏幕上的排版全部停止修复」这一可见变化。
- **两层之间整份覆盖，不逐键合并**，沿用 `spec/rules.md`「来源与优先级」中的「一次运行只有一个来源生效」；再设计逐键合并 (`disable` 是并集还是替换、`severity` 如何叠加) 只会增加一批需要定义、测试和解释的边角。
- **只有 hook 读取用户级，CLI 不读**：CLI 输出要能在本机、CI 与消费仓的 pre-commit 之间复现，一份只存在于某人家目录的文件会让本地与 CI 分叉；hook 修的是此人屏幕上的回复。
- 一个「不读仓级、只认用户级」的开关，键名与默认值届时再定。

### 四、退役的旋钮与状态

- 环境变量：`LIMAE_HOOK_MIN_CHARS`、`LIMAE_HOOK_AB_RATE`、`LIMAE_HOOK_TIMEOUT` 退役；`LIMAE_HOOK_DISABLE` 保留。`LIMAE_ENGINE` 与 `[polish]` 表仍只归 `limae polish` 管。
- 会话态目录中的 `ab/` (A/B 台账) 与 `polish/` (单路记录) 不再写入；`pending.json` 不再产生。它们的边界规则由 §二承接，用于约束保留的原文分片与诊断行。
- 中文双字编号词表 (`rust/hook/ab.rs` 的 `CODE_NAMES`)、候选池 (`CANDIDATES`)、`Stop` 回注 (`ab::context`) 全部失去用途，随下一个任务删除。

### 五、diagnostics 仍记，只记失败，Step 与 Kind 重定

`diagnostics.jsonl` 的四个字段 (`at`、`message_id`、`step`、`kind`) 与「只写 step 和 kind、不写正文」的边界不变。变化在于取值集合 —— 本节是 orchestra 在 brief 中预判的部分，预判为「`Single` / `Ab` / `Record` / `Assemble` 与 `Incomplete` / `Misconfigured` 失去来源」，读完代码后，前四个 Step 的判断成立，两个 Kind 被推翻，另加一个：

| | 处置 | 理由 |
| --- | --- | --- |
| Step `single` / `ab` / `record` | 删 | 没有引擎调用、没有 A/B、没有记录，这三步都不存在了 |
| Step `assemble` → `siblings` | 改名 | 它等待的是兄弟批次的原文分片，拼的是截至当前批的前缀，不再是「整篇」；名称要表达它做的事 |
| Step `fix`、`display` | 留 | 运行规则、顶层崩溃仍在 |
| Kind `Engine(…)` 九种 | 删 | 没有引擎；`FailureReason` 本身留在 `rust/polish/` 供 CLI 使用 |
| Kind `repaired` | 删 | 它记录「规则改动了模型的重写」，属于选型信号；现在改动就是 hook 的职责 (读数 D：一半批次会改)，记录它只是噪音 |
| Kind `incomplete` | **留** (预判说删) | 兄弟批次到期未齐仍会发生，而且从「只在末批」变为「每一批都可能」，它是 §二第 1 步「等不齐就不修」的名称 |
| Kind `config` (`Misconfigured`) | **留、换来源** (预判说删) | 旧来源是 `[polish]` 表；新来源是 §三的仓级规则配置无法读取 (不是合法 toml，或违反 `spec/rules.md`「配置错误」清单)。将其并入 `crashed` 会把用户自己的 toml 笔误报成「这是 bug，请报」，让人往错误方向查 |
| Kind `partial` | **新增** | §二第 3 步第一道：行边界不完整 —— 前缀不以 `\n` 结尾，或中间批自身不以 `\n` 结尾。下一步应核验读数 A：宿主的分批行为变了 |
| Kind `unclosed` | **新增** | §二第 3 步第二道：尾部可能仍在一个行内代码 span 中，等待下一批。它不是故障，而是正常现象 —— 开反引号写在行尾时每次都会触发一次 |
| Kind `crashed` | 留 | 顶层崩溃与状态目录不合作 |

改后 Step 三个 (`siblings`、`fix`、`display`)，Kind 五个 (`incomplete`、`partial`、`unclosed`、`config`、`crashed`)。`tools/check_repo_contracts.sh` 承诺 2 (手册 `kind` 表覆盖代码全集，全集由 Cargo example `hook-kinds` 打印) 保留，改造时它会正确报红，直到手册表格同步 —— 这是预期的红。`hook-kinds` 中 `Engine(REASONS)` 那一臂随 `Kind::Engine` 一起删除。

### 六、Codex hook 废弃，连同它的契约

`.codex/config.toml` 删除；`rust/hook/cli.rs` 的 `codex_stop` 与 `is_codex_stop` 删除；`tools/check_repo_contracts.sh` 承诺 1 (Codex `Stop` 钩子未构建时 fail open、构建后透传退出码) 删除。删除这条契约本身需要两臂验收：先删 `.codex/config.toml` 而不改脚本，检查必须报红 (证明它确实在检查)；再删脚本中承诺 1 那段，检查通过。`docs/knowledge/polish-hook-self-trial.md` 的 Codex 一节与 ADR-0014 的「实测」一节保留为历史记录，前者在手册改写时整节删除，后者 ADR 不改。

### 七、polish 不删也不被取代：hook 不再调它，它自己有两条路径

**只改一件事：hook 不再调 polish。** `rust/polish/`、`limae polish` 子命令、`spec/polish/` 的两层 prompt、`[polish]` 表、`LIMAE_ENGINE`、引擎探活与隐私边界 (ADR-0008 §三、§四、§六 CLI 部分、§七、§八、§九) 均不变。hook 改造后，`rust/` 下引用 `crate::polish` 的只剩 `rust/cli.rs` 的子命令分发；当前 `rust/hook/` 从 polish 借用的两个小工具 (`polish::value` 读取环境变量、`HOOK_DISABLE_VARIABLE` 常量) 是否迁移，由实现任务决定，它们与引擎无关。

polish 此后有**两条并列的消费路径、一个源文件**：

- **CLI，headless**：`limae polish -` 保持不变，谁想运行都可以运行，脚本和其他工具都能调用。
- **生成出来的 skill**：供人装入自己的 agent，让模型在写作时就遵守规则 —— 与 ADR-0005 §一的 agent-native 定位同向，coding agent 使用 skill 比事后调用一个 CLI 更 native。

两条共用 `spec/polish/general.md` 与 `spec/polish/zh.md` 这一份源文件，它们本来就是「可整体替换的 spec 文件」(ADR-0008 §九)；skill 从它们生成，不另写一份。**本 ADR 不将 polish 描述为「被 skill 取代」**，那是错的。skill 的形态、生成方式、位置和分发属于后续 ADR，安排在 polish 的 prompt 再测一轮之后，这里不规定任何契约细节。

### 八、被取代的 ADR 逐份处置

按本仓规矩，ADR 被新 ADR 取代后不就地改写，各份仅在「状态」节新增一行指向这里：

- **ADR-0009**：§二 (按批缓存、末批整段改写、短消息阈值)、§三 (A/B 双模型对照)、§四 (中文双字编号)、§五 (`Stop` 回注)、§八 (引擎隐私边界与台账风险面) 由本 ADR 取代。§一 (挂 `MessageDisplay`、display-only 的推论)、§六 (fail-open)、§七 (先本仓自试再交 machine-setup) 的内容由本 ADR §一承接并成为唯一依据 —— 被取代的 ADR 不能再作为依据，指回去只会把读者带到一份大半失效的文件。§七所述路径本身仍成立：`.claude/settings.local.json` 先在本仓试，稳定后经 `machine-setup` 分发到用户级，本 ADR 不安排时间。
- **ADR-0011**：整份取代。其对象 (A/B 回注) 已不存在。其「后果」中「已采到的两轮判词不是盲评结果、不能当型号证据」仍是事实记录，不因取代而变化。
- **ADR-0012**：整份取代。brief 预判它是「部分修订而非取代，因为 `limae polish` 仍产出记录」，读代码后推翻：`record_run` 与 `RUN_DIRECTORY` 的唯一调用方是 `rust/hook/block.rs`，`limae polish` 子命令从不写会话态记录，因此 ADR-0012 的对象随 hook 的引擎调用一同消失。它对 ADR-0008 §十「不写盘」的澄清 (指不动用户文件、不产生旁路产物，不是不允许会话态临时状态) 仍然正确，本 ADR §二的原文分片正是按此理解存在。
- **ADR-0014**：整份取代 (§六)。
- **ADR-0008**：§十 P0 (hook 中的一次输出润色、A/B 挂在这里、§五的判据靠它采集) 由本 ADR 取代；§二 (三个子命令) 与 §六 (hook 失败就用原文) 不变。**§五 (模型默认由 A/B 决定) 的证据路径已不存在**，处置写在「后果」第一条。
- **ADR-0015**：不改。阶段 D 的表记录的是当时交付了什么，本 ADR 改造的正是那份交付物。

## 后果

- **ADR-0008 §五的缺口，明确写出，不假装不存在**：§五将默认型号的判据定为「用本仓与消费仓的真实中文段落做 10–20 条盲对照，采集手段就是 P0 的 hook A/B 模式」。这条采集手段已不存在，而且它从未产出合格证据 —— ADR-0011 记录此前采到的两轮判词不是盲评，随后 A/B 就被用户关闭 (`LIMAE_HOOK_AB_RATE=0`) 至今。处置是**冻结当前暂定默认** (codex `gpt-5.6-terra`、claude `sonnet`、grok `grok-4.6`，型号均可配置)，判据本身 (「降到便宜档必须有自家证据」) 不变，但**证据来源改为开放问题**：将来若要改默认型号，必须另建离线对照 (例如对同一批语料各跑两次 `limae polish` 后再人评)，不再有线上路径替它采样。§七两条路径中只有 CLI 还需要默认型号 —— skill 由写回复的模型自己遵守规则，没有型号可选 —— 因此这个开放问题的重要性变低，但没有消失。记录到 `docs/tracker.md`。
- **磁盘上仍保存流式消息的原文**：这是 §二明确写出的代价，边界完整继承自 ADR-0009 §八与 ADR-0012，由 `prune` 按年龄清理。
- **hook 此后不能观测「做了什么」**：ADR-0012 的记录用于比较模型改写的分布；机械修是确定性函数，同一输入始终得到同一输出，不需要分布；要测它的改动率，可按读数 D 的方法离线对 transcript 跑一遍 `--fix`，无需 hook 参与。诊断仍只记录失败。
- **代码会大幅缩小，这是预期，不是要求**：当前 `rust/hook/` 共 6724 行 (含测试)。A/B (`ab.rs` 与测试 1194 行)、块构建与引擎接线 (`block.rs` 与测试 1437 行)、改动渲染 (`render.rs` 及其 cases / tests 973 行，它渲染的是「润色改了几处」，机械修没有这一块可渲染) 整体失去用途；`state.rs`、`parts.rs`、`cli.rs` 分别保留更薄的一版，`parts::assemble` 与 `state::keep` 基本原样复用。实现任务按本 ADR 删除，不以行数为目标。
- **`docs/knowledge/polish-hook-self-trial.md` 整份都要改写**：Codex 一节、A/B 台账两节、反馈一节、旋钮表、`kind` 表均已过期；`.claude/settings.local.json` 示例去掉 `Stop` 与 `timeout`。README「LLM 语义润色」一节末尾的「还没做的：hook 形态与 A/B 采集」也已过期。两处由实现任务一并修改，不单独开 PR。
- **本仓的 `.claude/settings.local.json` 不入库**，当前正挂着 `tee` 采样，本 ADR 和实现任务都不碰它；改造合入后由用户自己删除 `Stop` 那项。
- **`tools/check_repo_contracts.sh` 从四条承诺变为三条**：承诺 1 删除 (§六)，承诺 2 保留且会在改造中报红一次 (§五)，承诺 3、4 (两个 pre-commit 钩子的 `files`) 不受影响。
- **ADR-0009 §七的分发计划不变**：稳定后经 `machine-setup` 将 hook 配置装入用户级 Claude Code 设置，不由本仓直接写入家目录。
- **不做的**：不改 `spec/`，规则语义一个字不动；不加用户级配置 (§三的开放项)；hook 中不写任何 Markdown 解析器 (围栏、span、指令的判断全部来自 canonical pipeline)；不为 Codex 寻找替代事件。

## 验收判据 (给实现任务)

每条都要有对照臂，「改坏则红」与「真产物仍被 accept」一起测：

1. **逐批等于整篇**：对全部黄金 fixture 与一组合成消息 (含围栏代码块，围栏内放读数 B 的两个形状 —— `status.success()`、`..limits() }`)，逐批喂给 hook (带 `session_id` / `message_id` / `index` / `final`，中间批以 `\n` 结尾；**一批可以有若干整行，不是一行**，用例必须有多行批，见读数 B′；跨行指令的 `inline-disable-*` 不排除，前缀重放本应将它们处理正确) 后再拼回，必须与整篇 `--fix` 逐字节相等 —— **仅一处允许不等**：命中 `unclosed` 的那批原样上屏，若整篇修会改那批中 span **之外**的正文，逐批结果就会少修这些位置，断言应将这种批的输出写为「等于 `delta`」。对照臂：强制将前缀置空 (删除兄弟批次文件)，围栏和指令的那些用例必须分叉，其余仍必须相等 —— 证明前缀决定这些用例，也证明其他用例不依赖它。语料使用合成文本与 fixture，不使用 transcript (回复原文不入库)。
2. **结尾逐字节保留**：末批不带 `\n`、中间批带 `\n`，修后输出的结尾与输入一致；末批为空则不输出。
3. **等不齐就不修**：缺一批的目录，到期后这批无输出，`diagnostics.jsonl` 多一行 `siblings` / `incomplete`；补齐后同一批有输出。
   **实例身份两臂** (Astra 的合成形状)：目录中留一份旧代 index 1 (内容为普通文本)，新代 index 0 已到、index 2 到达 —— 按 `turn_id` 分目录后，index 2 读不到旧分片，按缺批处理；同一目录下同 index 重送不同内容 → 这批和之后各批均无输出、各记 `siblings` / `incomplete`，重送相同内容 → 幂等、照常修。
   **资源上限两臂** (§二「成本」的三项上限分别测试)：正臂为刚好不超过上限的消息照常修，诊断不多一行；超限臂为超过上限的那批及之后各批均无输出、各记 `siblings` / `incomplete`，且此后批次**不得**截掉旧前缀后照常修 —— 对照方法是在超限后放一批围栏内代码，它必须原样上屏。
4. **两道当批 fail-open，各至少两批**。行边界：一条不以 `\n` 结尾的中间批，无输出、记 `siblings` / `partial`；**它之后补完整该行的那批**即使自身完好、包含可修违规，也无输出，也记 `siblings` / `partial`；再下一批 (从整行开始) 正常修。对照臂：相同批次，但第一批补上 `\n`，三批都正常修，诊断不多一行。span：按 `spec/fixtures/span-across-line-break` 的形状拆成两批，开反引号那批原文上屏、记 `siblings` / `unclosed`；闭合那批**不得改 span 内代码**，span 外正文 (`后文(y)` 那一处) 仍正常修。对照臂：同一段文字将开反引号和闭合放在同一批，该批正常修，不记 `unclosed`。
5. **配置照旧、配置错误 fail-open**：`cwd` 所在仓库有一份关闭某条规则的 `limae.toml` 时，该规则不修；没有时修；仓级文件不是合法 toml 时，这批无输出，记录一行 `fix` / `config`，而不是回退默认集照修。对照臂为同一批文本在合法配置下有输出。
6. **不碰家目录**：运行完一批后，`$HOME` 下没有新增任何 `limae` 相关文件或目录 (§三的开放项没有被顺手实现)。
7. **`Stop` 与 Codex `Stop`** 各喂一条，无输出，退出 0。
8. **契约门两臂**：§六的两步。承诺 2 在 `hook-kinds` 改后、手册改前报红，改后通过。
9. **十三道门裸跑全绿**，一条也不接管道，逐条检查退出码。

## 补记 (2026-09-11)

实现 PR #180 (head `6913b06`) 与 orchestra 同日的中断实测带来五条补充内容。正文各节不就地改写，以本节为准。

**一、三条实现期澄清。** 都不是偏离本 ADR，而是上文未写到、实现必须明确的行为契约：

- **末批不做 `unclosed` 判断**。§二第 3 步第二道的条件是「还可能被**未来的行**闭合」，末批没有未来的行。按字面理解会以为每批都要判断；按那个理解实现，每条以未配对反引号结尾的回复都会永久少修一处。
- **行内指令点名不存在的规则 id 时，`fix` 拒绝，归到 `config`，不是 `crashed`**。这种输入来自回复正文中的 `inline-disable-*`，§五的五个 Kind 表面上无法覆盖它。归为 `config` 的理由与表中保留 `config` 的理由相同：这是写作者自己的笔误，报为 `crashed` 等于让他往「报 bug」的错误方向找。`kind` 表由 `tools/check_repo_contracts.sh` 的承诺 2 约束，因此手册中的对应行要明确写出两个来源。
- **payload 缺 `turn_id` 时不输出**。它是 §二消息实例键的一半，缺失后无法判断分片属于哪次消息 —— 符合本 ADR「拿不准就不修」的方向。

**二、本 ADR 引用的所有分叉计数，都是某种切法下的读数，不是方案的固有属性。** §二引用了 Fable 在逐行切批下的「前缀重放 3 条分叉」，#180 用自己的切法 sweep 全部黄金集 (52 条 fixture × 3 种切法)，读到的是**触发 `unclosed` 10 条、拼回后与整篇不等 6 条**。两者不矛盾，区别在于切批方式：某条 fixture 在一种切法下将开反引号与闭合放进同一批时不会触发，换一种切法则会触发。

耐久的是**形状**，不是数字：#180 的 6 条全是同一形状 —— **被拒的中间批中既有未配对反引号，又有 span 外可修的正文**。数字会随切法变化，形状不会。`spec/fixtures/span-across-line-break` 被拒但不分叉，因为被拒的那批全在 span 内，正是同一形状的反面。

**这条应作为通则理解，不只针对这里。** 同一个问题这一轮出现三次：orchestra 的「逐行与整篇的唯一分歧来自围栏」被 Fable 指出是过度推广 (§背景「读数 B」末尾的限定正是那次指出后的结果)；Astra 主动将自己的结论固定在 head `b20bc03`，而非最终版 (它自己避免了这个问题)；#180 的 sweep 是第三次。因此：**引用任何分叉计数时，都要同时写明它在哪种切法、哪个 head 上测得；不要将其当作方案的绝对值。**

**三、§二「成本」中的三个上限 (256 KiB 原始字节 / 1000 分片 / 单次等待 2 s) 是估定的，不是测得的。** #180 没有进行新的计时测量：256 KiB 来自 Fable 的「200 KB 单次 151 ms」线性外推后取整为 2 的幂，1000 批参考 Astra 的 120 批与 Fable 的 598 批，均远在其内，2 s 则原样沿用既有的 `SIBLING_WAIT`。这三个数只说明「显然够用且有界」，**没有一个是从失效点测回来的**。后人要改它们，改的是 `parts::Limits::DEFAULT` 的三个常量，不必认为是在推翻什么 —— 目前它们背后没有任何测量。

**四、中断实测 (orchestra 2026-09-11 本机，隔离 lab 加采集 hook，esc 与 Ctrl-C 各一次)。** 读数为：**被打断的消息永远收不到 `final=true` 的那批**。因此，§二清理一节所说的孤儿分片**是常态，不是异常** —— 按年龄 prune 不是兜底，而是这条路径上唯一的清理者，必须真正承担这一职责。同一次实测也验证了 §二列为「由实现任务验证」的前提 ①：`turn_id` 在各批间一致 (70 条真实消息中 0 例不一致)，且随重发变化 (两次中断后 `message_id` / `turn_id` / `prompt_id` 三者均换新)。**未覆盖的一臂如实说明**：测的是「中断后人再发一条新 prompt」，不是「同一条消息被宿主自行重投」(API 错误重试那类)，后者没有样本。

**五、`message_id` 加 `turn_id` 之外的残余风险：用户于 2026-09-11 裁决接受。** 用户的意思是「我其实还是不理解这个风险是什么，但至少从这个描述来看，它成立的概率很低。不要 over-engineering，该做做就好」(语音输入，经 orchestra 转述，措辞表达原意而非逐字)。接受依据是以下三点，必须一起看：

1. **失效需要三个条件同时成立**：① 宿主对同一条消息复用 `message_id` 加 `turn_id`；② 两代内容不同；③ 第 `k` 批读取前缀时，某个内容不同的第 `j<k` 批尚未落盘。第 ③ 条措辞取自 #180 的实现方，比「index 0 输掉竞争」准确 —— 作废由**第一个到达且内容不同的新一代批次**触发，通常是 index 0，但不限于它。
2. **影响范围有限**：hook 的 `displayContent` **只改屏幕，不落盘** (§一引用 ADR-0009 §一的依据)。证据是 orchestra 于 2026-09-11 的实测：那 677 条回复原文来自 transcript，采集时 hook 正在运行，其中 52% 需要修 —— 说明 transcript 保存的是未经 hook 改动的原文。因此最坏后果是「某批围栏内的代码在屏幕上多一个空格，且无法撤回」，不污染 transcript、不污染任何文件，也不进入模型上下文。
3. **证据等级必须原样保留**。orchestra 检查过 Claude Code 二进制 (218 MB；grep 有分辨力，对照臂 `hookSpecificOutput` 命中 40、`displayContent` 命中 11)，**能够确定**的是：客户端区分 client 侧与 API 侧两个 message id 空间，重试存在且单独记账。**不能确定**的是：重投时 client 侧 `message_id` 是否改变。**字段名不是语义** —— 这条「能 / 不能」的边界不要压缩成「大概率会换」。

**这不是「已排除」，也不是「已验证安全」。** 它是一个被明确接受的**已知残余风险**，接受理由是概率低且影响范围有限，不是它已被证伪。将来若真观测到一次，应回到本节，不要当作新发现。
