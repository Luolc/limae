# 事故记录：脱敏映射的原值进了提交信息与 PR 文本 (2026-08-31)

## 发生了什么

本仓从 wealth-management 迁入 Python 参考实现期间，一次迁移 PR (PR #2) 对代码内容做了正确的脱敏处理，但「旧值 (原始理财细节) → 新值 (合成占位符)」的映射被直接写进了两处文本：

- 该 PR 分支上一个 transfer 提交的 commit message。
- 合入 `main` 时使用的 squash 提交 message (第 20–21 行)。

这两处 message 各含 5 个原值 (券商名 ×3、金额、股数)，均为用户真实理财细节，不是本仓允许的合成 fixture 数据。

## 怎么发现的

复查 `main` 的 squash 提交时，发现其 message 正文含上述原值。顺藤摸瓜确认：

- PR #2 分支上的 transfer 提交同样含原值；分支本身已删除，但 GitHub 为每个 PR 保留 `refs/pull/<N>/head` 引用——即使源分支删了，该提交仍可经这个引用在 PR 的「Commits」页公开查看，且用户无法自行删除这个引用 (需联系 GitHub Support)。
- PR #2 描述此前已被实现方编辑修正为不含原值的版本，但 GitHub 会保留每一次编辑的历史版本 (UserContentEdit)，public 仓库任何人都可以点开「edited」标记查看修改前的内容；删除某条历史版本是仅限网页 UI 的操作，未发现对应的 API。
- 仓内被 git 追踪的文件与 PR 评论区：排查 0 命中，问题只存在于提交信息与 PR 描述文本。

## 处置

用户裁决：不在原仓修补 (改写受保护分支的提交信息、清理 PR 编辑历史等半吊子方案仍会留下 `refs/pull/2/head` 这类无法自行清除的公开引用)，而是删除整个仓库并重建。重建后的仓库只保留一个干净的 initial commit，不带任何历史，本次事故涉及的提交与 PR 引用随旧仓一起被移除。

## 根因

派活时的 brief 与 agent 间的 herdr 提示里，直接写出了「旧值→新值」这份脱敏映射本身，实现方在撰写提交信息与 PR 描述时照抄了这份映射的内容。审查方核对的是变更文件的内容是否已脱敏，没有把提交信息与 PR 描述文本纳入检查范围，因此没能拦住。

## 教训与新规则

敏感值 (原始理财细节等) 不应该以任何形式出现在自动化流程接触到的文本里——不只是仓内文件，brief、herdr 提示、commit message、PR 描述与评论同样是「文本」，一旦写入公开仓库的 PR 或提交历史，事后清理的代价远高于事前避免 (`refs/pull/<N>/head` 与 PR 编辑历史都不是用户可自行删除的)。

新规则 (已写入 `AGENTS.md` 「隐私边界」)：敏感值不进 brief / PR 描述 / commit message / 评论等任何文本，只按位置指代 (文件、行号、测试 id 等)；脱敏映射本身只留在裁决人手里，不经任何 agent 间通道传递。
