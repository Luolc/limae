# 裁决：跨批「在不在围栏里」 —— 候选二 (前缀重放) 对，但要换掉它自己给的理由

> 归档说明：本文件由 orchestra 于 2026-09-11 从 `~/scratch/limae/debate-fence-fable-2026-09-11.md` 原样归档入库到 `docs/research/`，正文一字未改。裁决方读的 head 是正文自己声明的 `0f70af8` (worktree `~/wt/limae/debate-b`，detached)，与 Astra 裁决方钉的 `b20bc03` 不同 —— 两份报告各自独立声明自己的 head，不互相对齐，读者结合两者时请留意这一点。本文件没有旁支脚本文件需要内联 (orchestra 已 grep 正文，未发现 `~/scratch` 或 `/home/ubuntu` 的路径引用)。

裁决方：limae-debate-fable，模型 Claude Fable 5.1。worktree `~/wt/limae/debate-b` (detached，`0f70af8`)，release 构建 `target/release/limae`，2026-09-11 dev-oregon 实测。实验脚本在本会话 scratchpad (`harness.py` / `exp2.py`)，方法全部写在下面，可以照着重跑。

## 一句话

**候选二对。** 但它的核心论据「crate 里已有一套处理 `~~~`、更长围栏、3 空格缩进、闭合不短于开启、4 空格缩进代码块的块解析器」**是错的** —— `render::prose_length` 与 `markdown.rs` 用的都是同一个「去掉行首空白后以 ``` 或 `~~~` 开头就翻转」的布尔，不认识上面任何一种。候选二胜出的真实理由是我跑出来的：**跨批状态不止围栏一个**，行内指令 (`limae-disable`)、跨行反引号 span 的闭合、引用块延续都是前缀决定的；候选一只带围栏，在 52 条黄金 fixture 逐行切批时 7 条与整篇分叉，候选二 3 条，而候选二剩下的 3 条是**任何按批方案都消不掉的** (后一行改变了前一行的保护，前一行已经上屏)。另外候选二撞上 partial 批时下一批就恢复，候选一按 ADR §二 要整条消息 fail-open。

## 1. 哪个对 —— 证据表 (标明跑出来的 / 推理的)

### 1.1 跑出来的：黄金 fixture 切批重放

方法：52 条 `spec/fixtures/*.in` (带 `.conf` 的把 conf 写成临时目录的 `limae.toml`，临时目录放一个 `.git` 截断向上查找)，先验证整篇 `--fix` == `.fixed` (52/52 通过，这是 harness 的 sanity 臂)。再按行边界切批，三种切法：每行一批 (`one`)、每两行一批 (`two`)、种子随机 1–4 行一批 (`rand`，seed 20260911)。

- 候选一模拟：前缀里围栏行数 (与 `markdown.rs` 同一判据：`is_python_whitespace` 剥掉行首后 `starts_with("```") || starts_with("~~~")`) 取奇偶；奇则在这一批前拼一行 ` ``` ` 再修、修完剥掉 (ADR §二 自己列的等价做法之一)。
- 候选二模拟：brief 里的五步，含「前缀非空且不以 `\n` 结尾 → 原样输出」补丁与 `lines(T') != lines(T)` 守卫。

| 切法 | 候选一分叉 | 候选二分叉 |
| --- | --- | --- |
| 每行一批 | 7 | 3 |
| 每两行一批 | 3 | 0 |
| 随机 1–4 行 | 3 | 1 |

分叉的 fixture 与分类 (每行一批那次)：

| fixture | 候选一 | 候选二 | 状态来源 |
| --- | --- | --- | --- |
| `inline-disable-range` | 分叉 | 一致 | 行内指令跨批 |
| `inline-disable-next-line` | 分叉 | 一致 | 行内指令跨批 |
| `inline-disable-config-boundary` | 分叉 | 一致 | 行内指令跨批 |
| `span-closes-at-line-start` | 分叉 | 一致 | 反引号 span 在前一批开启、这一批闭合 (闭合行的修法取决于前缀) |
| `span-opens-at-line-end` | 分叉 | 分叉 | 开启行已上屏，闭合行后到 —— **不可消除** |
| `span-across-line-break` | 分叉 | 分叉 | 同上 |
| `span-across-blockquote-lines` | 分叉 | 分叉 | 同上，叠加引用块延续 |

读法：候选二消掉了所有「这一批的修法取决于前缀」的分叉；剩下三条是「前一批的修法取决于后一批」，按批显示的合同里没有任何方案能做到 (除非不显示，那不是 `MessageDisplay` 允许的)。这三条的方向是**按批比整篇多修** (把跨行行内代码里的 `你好,世界` 修成 `你好，世界`)，是改到了「行内代码」，但跨行的行内 span 在助手回复里极少见；两个候选在这三条上表现相同，不构成区分。

### 1.2 跑出来的：partial 批

- 未打补丁的候选二，批次 `['中A', '中B\n中C\n', '中D']` 输出 `中 A中 A 中 B\n中 C\n中 D` —— **屏幕重复**，候选一作者挑的洞是真的。
- 打补丁后输出 `中 A中B\n中C\n中 D`：第二批原样放行 (少修一行)，第三批恢复正常。整篇是 `中 A 中 B\n中 C\n中 D`。
- 围栏开启行被拆成两批 (前一批是两个反引号，后一批是第三个反引号加 `rust` 加换行)，再接四批：一行 `fn main()`、一行闭合围栏、一行 `中A(x)`、末批 `中B`：候选二第二批原样放行，**第三批起前缀已经是 ` ```rust\n `，围栏状态正确**，代码不动、后面的散文照修，最终与整篇逐字节相同。候选一按 ADR §二「无效标记向后传播」，同一消息其余各批全部原样放行。**这是两个候选行为真正不同的第二处**：候选二的失败面是一批，候选一的是整条消息的剩余部分。

### 1.3 跑出来的：成本

release 构建，CLI 进程启动本身约 15 ms (空文件)。合成中文文档 (每段带违规 + 一个围栏)：

| 大小 | 行数 | 整篇 `--fix` |
| --- | --- | --- |
| 13 KB | 200 | 18 ms |
| 50 KB | 750 | 95 ms |
| 100 KB | 1500 | 77 ms |
| 200 KB | 2990 | 151 ms |

100 KB 切成 598 批 (随机 1–4 行) 全程重放：候选二总 CPU 28.0 s (平均 47 ms / 批，末批最贵约 90 ms)，候选一 13.4 s (平均 22 ms / 批，几乎全是进程启动)。候选二是 O(n²) 总量，但**每一批**都远在宿主 10 s 默认超时之下，且这些 CPU 摊在消息流式输出的几分钟里。两种重放拼出的结果都与整篇相同 (合成文档里没有跨行 span)。

### 1.4 推理的

- **候选二几乎不需要新代码**：今天的 `state::keep` 存的就是 `delta` 原文，`parts::assemble(parts, k)` 返回的就是第 0..k-1 批的拼接，即候选二的 P；兄弟批等待 (`SIBLING_WAIT` 2 s / `SIBLING_POLL` 20 ms) 也在那里。候选二 = `assemble` + `Pipeline::fix(P + delta)` + 取尾。候选一要新文件格式、无效标记、向后传播、`Pipeline::fix` 加入口状态参数 (或合成围栏)，四件都是新代码，每件都要两臂验收。
- **「磁盘上没有回复原文」这个候选一的优点是真的，但边际收益小**：宿主自己把整份 transcript 落在 `~/.claude/projects/**/*.jsonl`，比 `$TMPDIR/limae-hook` 的 1 小时 retention 长得多、权限也不比它严。候选二不是退步 (今天就落盘)，边界规则 (`0700` / `0600` / 先写临时名再 rename / 不落 checkout / 1 小时 prune) 原样继承即可。
- **围栏之外的状态本来就存在于 `markdown.rs`**：`protect` 里除 `in_fence` 外还有 `paragraph` (跨行反引号配对) 与 `continues_quote`；`rule_masks` 里有指令状态。候选一的 ADR 把它们列为「明知的、预期的分叉」，读数 B/C 的 250 篇里恰好没出现 —— 1.1 的 fixture 证明它们不是理论问题。

## 2. 候选二还有的洞 (逐条)

1. **并发**：brief 的五步没写「等」。宿主并发派发各批 (`parts.rs` 模块注释，2026-09-01 Claude Code 2.1.257 实测)，第 k 批必须像今天的 `assemble` 一样等第 0..k-1 批的文件齐 (到期不齐 → 原样放行、记 `incomplete`)。这不是新洞，是必须显式写进方案的一句。
2. **末批删目录的竞争**：今天末批 `remove_dir_all(parts)` (`rust/hook/cli.rs:255`)；改成每批都读前缀后，末批删目录会让还在等的早批读到「目录不存在」。ADR §二 已经指出、改由 `prune` 按 `ORPHAN_RETENTION` 扫 —— 候选二要照抄这一条。
3. **`message_id` 复用**：两个候选暴露面相同 (陈旧文件被当成本消息的)。宿主 id 在测试样本里是 UUID 形状；真实 payload 我核不到 (末批已删目录，磁盘上 18 个 session、0 个残留 message)。**不要**让 index 0 去清目录 —— 并发下 index 1 可能已先写入，清掉就是白等 2 s 后 fail-open。靠 id 唯一 + 1 小时 prune，与候选一同一水位。
4. **非常大的消息**：见 1.3，200 KB 单次 151 ms；总量 O(n²) 但每批有界。若某天真有 1 MB 级的回复，加一条「前缀超过某阈值 → 这一批原样放行」的 fail-open 即可，阈值届时实测。
5. **CRLF**：CLI 的 `files.rs:112` 把 `\r\n` 归一成 `\n`，**hook 走的 `Pipeline::fix` 不归一** (`parts.rs::fixed` 直接调 pipeline)，`\r` 留在行尾当普通字符；行数按 `\n` 数，取尾不受影响。宿主发的是 LF。两个候选相同。
6. **嵌套围栏 / 围栏变体**：实测 linter 自己的行为 —— ```` 外层里的 ``` 会把外层「关掉」(中间的 `中B` 被当散文修)、``` 里的 `~~~` 同样、4 空格缩进代码块**不豁免** (`    fn main()` → `    fn main ()`)、缩进 4 空格的 ``` 仍算围栏、闭合短于开启也算闭合。这些都与 `spec/rules.md` 「全局豁免」第 1 条一致 (规范就只认这两个前缀)，是规范的取舍不是实现 bug；两个候选与 linter 完全一致，不构成区分。但要指出：**候选二的论据里说 crate 有更完整的解析器，没有。**「两套真相来源会漂移」这个论证本身仍成立 —— `markdown.rs` 与 `prose_length` 已经是两份同样的 toggle，候选一会加第三份。
7. **行内指令跨批**：候选二免费拿到 (1.1 三条 `inline-disable-*` 全部一致)。所以 ADR §二 那条「预期分叉臂」在候选二下要**反过来写**：逐批必须等于整篇，红了才是 bug。
8. **取尾的实现细节**：`lines()` 与「最后 n 行」必须用同一个定义 (只按 `\n` 切，末批无 `\n` 时最后一行不带 `\n`，`delta` 为空则 n = 0 输出空)。`lines(T') != lines(T)` 那条守卫今天恒不触发 (见 4.D)，留着当未来规则的保险，成本为零。

## 3. 有没有更好的第三个

**有一个在理论上更好、今天不值得做的**：把 `Markdown::protect` 与 `rule_masks` 改成可续跑 (resumable) 的扫描器，每批把扫描器状态序列化到磁盘 —— `in_fence`、段落是否开着、上一行是否引用行、当前段落里的反引号串长度序列 (配对算法要整个序列，不是栈)、指令启用集。它是**唯一真相来源** (同一段代码)、O(n)、磁盘上没有原文。代价是重构 linter 的核心扫描器并暴露状态，比两个候选都大；按「第三次重复才允许抽象」，等候选二的 O(n²) 或落盘真成为问题再做。ADR 里可以留一句指针。

「候选二但只存到上一个状态复位点」这类折中不值得：找复位点本身就要解析，绕回候选一。

## 4. 读数 A–F 复核

- **A (批边界落在行边界)**：判据有分辨力 (对照臂是 6 条末批全不以 `\n` 结尾)。另有一条独立佐证：`parts.rs` 模块注释记的宿主行为是「fires once per batch of newly completed lines」。结论没被过度推广，但样本是一个 session 58 条；候选二对它的依赖比候选一轻 (partial 只毁一批)。
- **A′、B′**：无法复跑，接受；B′ 与 1.1 一致 (我的切法就是多行一批)。
- **C (逐行 ≈ 整篇，248/250)**：判据有分辨力 (抓到了 2 条)。**结论「唯一分歧来自围栏」被过度推广**：这是那 250 篇的性质，不是 fix 的性质 —— 1.1 在 fixture 上找出另外四类分叉 (指令三条、span 三条、引用块延续一条)。C 支持「按批可行」，不支持「围栏是唯一状态」。ADR-0016 把这条叫读数 B，brief 叫 C，编号对不上，读的人要留神。
- **D (`--fix` 不改行数)**：677/677 且有对照臂，判据成立。更强的是它是**代码不变量**：`Pipeline::fix` 按 `\n` 切、逐行 `fix_line`、按 `\n` 拼；`rust/rules/` 里没有任何规则往输出里放 `\n` (grep 只命中 `tells.rs` 的测试与 `take_while`)。所以候选二的行数守卫今天永远不触发，留着是给未来规则的。
- **E (13 ms)**：复现 —— 13 KB 18 ms，其中约 15 ms 是进程启动，修本身只有几毫秒。E 量的是整篇一次；候选二每批都修一次前缀，200 KB 也只到 151 ms。
- **F (未闭合围栏受保护)**：三臂复现，读数与 brief 逐字相同 (`fn main()` 只在无围栏的对照臂被改成 `fn main ()`)。

## 5. 给实现任务的建议 (若采纳候选二)

1. 保留 `keep` / `assemble` / `SIBLING_WAIT` / 状态目录全部边界规则；末批不删目录、交给 `prune`。
2. 每批：`assemble(0..k-1)` 得 P；P 非空且不以 `\n` 结尾 → 原样放行、记 `partial`；否则 `fix(P + delta)` 取最后 `lines(delta)` 行；行数不等或 fixer 失败 → 原样放行。
3. 验收判据把 ADR §二「预期分叉臂」改成「逐批等于整篇」，用 1.1 的方法：52 条 fixture × 三种切法，允许分叉的只有 `span-opens-at-line-end`、`span-across-line-break`、`span-across-blockquote-lines` 三条 (且只在每行一批时)，把它们写成命名的预期分叉臂；其余 49 条必须逐字节相等。对照臂：删掉前缀 (P 恒空) 时围栏 fixture 与 `inline-disable-*` 必须分叉。
4. 加 partial 恢复臂：拆开的围栏开启行 (1.2 第三条)，第三批起必须与整篇一致。
